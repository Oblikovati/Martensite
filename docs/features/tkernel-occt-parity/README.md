# tkernel performance parity with OCCT TKernel

Requirement (maintainer, 2026-11-21): every public `martensite-tkernel` API must be as
fast as its OCCT 8.0 `TKernel` counterpart or faster. An API counts as public only when
another toolkit calls it. The internal design is free: use Rust designs and established
crates. A public API change is allowed when its measured gain justifies the break.

This note is the inventory that starts the work. Reviewed tree: `main` at `d63ef7bc`
(`martensite-tkernel` 0.4.5). OCCT: 8.0.0 built with `-O3 -DNDEBUG` from `../OCCT`.

## Measured gap

Paired micro-benchmarks, one C++ program against the installed OCCT and one Rust program
against `martensite-tkernel` in release, each doing the same work with the same checksum.
N = 1,000,000, median of 7 repeats, pinned to CPUs 8-15, average of two runs per side.
Single thread unless the case says otherwise.

| Case | OCCT ns/op | Martensite ns/op | Ratio |
| --- | ---: | ---: | ---: |
| `IncAllocator` allocate 32 bytes | 2.56 | 350 | 137 |
| `Sequence` append | 8.0 | 742 | 93 |
| `List` append and iterate | 8.7 | 791 | 91 |
| `Sequence` iterate | 1.18 | 85.6 | 73 |
| `AsciiString` append and search | 13.6 | 514 | 38 |
| Progress scope, null range | 0.8 | 10.9 | 14 |
| `Sequence` value(i), ascending | 2.5 | 16.4 | 6.5 |
| `DynamicArray` append | 0.73 | 4.45 | 6.1 |
| `DynamicArray` value(i) | 0.48 | 2.1 | 4.5 |
| `Handle` clone | 9.2 | 32.1 | 3.5 |
| `Handle` create | 18.2 | 52.1 | 2.9 |
| `DataMap` bind | 15.2 | 36.4 | 2.4 |
| `IndexedMap` add | 20.9 | 35.2 | 1.7 |
| `DataMap` seek, `IndexedMap` find | 1.7 | 1.9-2.0 | 1.1 |
| Parallel for, 64 items per launch | 18,090 | 17,137 | 0.95 |
| Parallel for, per item | 31.5 | 23.6 | 0.75 |

The profiles name three causes. The allocator emulates C++ virtual dispatch on every call:
it checks the runtime type chain of the allocator kinds, creates and drops a handle observer,
and records each heap block in a locked hash map. `Sequence` and `List` record each node in
a side hash table keyed by its address, with Rust's default SipHash (17% of the time), and
every node goes through that allocator path. `Handle` projects the runtime type on every
access and keeps two reference counts, the `Arc` count and the native count.

## Replacement candidates

A crate replaces an internal only when it keeps the observable behavior that callers depend
on. Three behaviors rule out several popular crates.

- `Map`, `DataMap`, `DoubleMap`, `PackedMap` and the flat maps
  walk their entries in OCCT bucket order, and ported algorithms (Booleans, sewing) produce
  their output in that order. `tests/map_traversal_order.rs` pins it. `hashbrown`,
  `indexmap` and `std::collections::HashMap` walk in a different order, so they cannot
  store these maps. The OCCT algorithm can: prime bucket counts, insertion at the bucket
  head and the same rehash, with the nodes in one `Vec` instead of separate allocations.
- `Vec2`-`Vec4`, `Mat3` and `Mat4` document a fixed
  evaluation order, so their results are bit-identical across builds. `glam` and `nalgebra` use SIMD and other orders, which change result
  bits.
- `CFormat`, `AsciiString::from_real`, the STL emulation
  (`mt19937`, `uniform_real_distribution`, the unstable order of libstdc++ `std::sort`)
  and the murmur and FNV hashes reproduce exact OCCT or glibc results.

(`tk-candidates`, release, CPUs 8-15, two runs):

| Case | OCCT | Martensite | Candidate | Design |

| Sequence append | 8.0 | 742 | 1.4 | node arena, slots linked by index |
| Sequence append | 8.0 | 742 | 0.31 | `Vec` |
| Sequence append and iterate | 9.2 | 828 | 4.9 | one heap node per item, fixed addresses |
| Sequence iterate | 1.18 | 85.6 | 1.34 | node arena |
| List append and iterate | 8.7 | 791 | 2.6 | node arena |
| Handle create | 18.2 | 52.1 | 13.9 | `Arc` |
| Handle clone | 9.2 | 32.1 | 9.0 | `Arc` only |
| Handle clone | 9.2 | 32.1 | 17.8 | `Arc` plus a native count |
| DataMap bind | 15.2 | 36.4 | 5.1 | OCCT bucket order on a `Vec` |
| DataMap seek | 1.72 | 1.93 | 1.37 | OCCT bucket order on a `Vec` |
| DataMap bind | 15.2 | 36.4 | 21.6 | `hashbrown` with `foldhash` (other order) |
| IndexedMap add | 20.9 | 35.2 | 45-53 | `indexmap` with `FxHash` |
| DynamicArray append | 0.73 | 4.45 | 0.35 | `Vec` |
| IncAllocator, 32 bytes | 2.56 | 350 | 5.2 | `bumpalo` |

| Progress scope | 0.8 | 10.9 | 2.7 | plain structs |

A design with one heap node per item, which keeps OCCT's address-stable nodes, already
beats OCCT. The cost of `Sequence` and `List` comes from the layers around their nodes.

## Accepted public API changes

The maintainer accepted these four changes on 2026-11-21. Each one names its consumers and
the measured gain.

1. `Handle::ref_count` (6 toolkits) and
   `StandardTransient::{increment, decrement}_ref_counter` (tests only) keep a native count
   beside the `Arc` count. Taking `ref_count` from `Arc::strong_count` keeps every
   signature and halves the clone cost (17.8 to 9.0 ns). Static handles and handles built
   from raw objects need a check that their reported counts stay the same.
2. Only `tkservice` and `tkv3d` call the raw `Sequence` and `List` node functions
   (prepared nodes, controlled clear, native cursors, node retirement, `current_node`).
   Option A keeps them on a node-per-item design without side tables and reaches parity
   (4.9 ns against 9.2 for append and iterate). Option B moves them into a type owned by
   those two toolkits and lets `Sequence` and `List` use the node arena: 2.7 ns against
   4.9 ns for append and iterate, 1.8 times faster than option A. Accepted plan: build A
   first, then decide B with geometry workload measurements.
3. `AsciiString::buffer_identity` has one consumer (`tkv3d`). It makes every edit of
   every string take a write lock. Replacing it with a borrow-based check lets the string
   be a plain byte vector: 514 ns to below 1 ns for the append and search case.
4. 3,821 public functions have no caller in another toolkit's code. Making them
   crate-private is a semver break (a minor release before 1.0). Speed does not need it;
   it removes the duty to keep each one at parity and frees the internal design.

The allocator needs no break: `AllocatorInvocation::{capture, allocate_base}` and
`BaseAllocator::storage_lease` (`tkservice`) and `BaseAllocator::from_handle` (`tkmesh`,
`tkservice`) stay as the custom-allocator variant, and the built-in policies reach parity
without them.

## Parity harness

`cargo xtask occt-parity --occt <prefix> --cpus 8-15` compares the cases of
`crates/martensite-tkernel/benches/occt_parity/` with their C++ twins in its `occt/`
directory. It builds the Rust cases as a release bench target, compiles the C++ files with
`-O3 -DNDEBUG` against `<prefix>/include/opencascade` and `<prefix>/lib`, then runs the two
programs in turn, OCCT first, for `--rounds` rounds (default 2) on the given CPUs. Each
program prints `name<TAB>median ns per op<TAB>checksum` for every case (1,000,000 items,
median of 7 runs). The command prints a Markdown table, writes
`target/occt-parity/tkernel/report.json`, and fails when the two sides report different
case names or checksums, or when a Rust case is slower than OCCT by more than `--tolerance`
(default 0.05). `--filter <text>` keeps the matching cases. Keep builds and other loads off
the measured CPUs.

OCCT is not a CI dependency, so this is a local gate. Without `--bench`, the Rust program
runs each case once at 1,000 items, which checks that the cases still work.

## Wave 2 parity progress (#590, #589, #587, #591, #583)

- **#590 (`ProgressScope` null-range fast path):** `ProgressRange::is_unbound`, `ProgressScope::from_range`, `ProgressScope::is_active`, `ProgressScope::next`, and `ProgressScope::close` short-circuit unbound ranges without touching `Cell` or `AtomicBool` loads/stores.
- **#589 (`DynamicArray` append and value):** `DynamicArray` caches `increment_shift` and `increment_mask` for power-of-two block strides so `element_coordinates` uses single-cycle shift/mask instead of 64-bit integer `DIV`/`REM`.
- **#587 (`DataMap` / `IndexedMap` insertion hot path):** `SlotChains::push_front` links and pushes in one write without dummy-slot overwrite, and hot lookup/insert helpers are marked `#[inline]`.
- **#591 / #583 (public surface audit):** Unconsumed internal helpers are tracked in `consumed-public-api.tsv`; narrowing proceeds incrementally behind workspace-wide compile verification.
