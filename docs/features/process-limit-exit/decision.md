# Process CPU-budget termination

Bug #278 restored the existing promise that an expired process budget prints its declared diagnostic and exits with code 2. A CPU cap had been installed without its signal action, so the operating system terminated the process with a signal instead. The elapsed watchdog already kept the promised behavior.

The foundation OS adapter now owns the CPU request, signal action and resource update. Process-policy delegates through a safe interface and retains its existing public API. There is one atomic requested value. Setters serialize outside the signal action; they publish that value before lowering a cap, so a limit that expires immediately can report the new request. A refused OS update deliberately retains the requested value and its typed I/O cause. The reported request can therefore differ from the effective OS limit after refusal. Signed `Some` values retain the existing cast to the host unsigned resource domain; `None` requests an unlimited cap. Separate direct-OS and policy children compare the signed edge cases on each platform. Successful concurrent updates leave the two values coherent.

The signal action and diagnostic relay are initialized before the resource cap. The relay confirms that its own thread blocks CPU-expiry and broken-pipe signals before setup can complete. Only successful initialization is retained: a temporary descriptor or thread-start failure returns its I/O cause and leaves the OS cap unchanged, so a later request can retry after resources are released. A private nonblocking channel stays owned for the process lifetime; the action reads a lock-free atomic request and sends its fixed-size snapshot without allocation, locks or destructors. The relay formats the bounded diagnostic. Other Unix targets write directly to the output descriptor, bypassing Rust's stdout mutex. Darwin uses an isolated writer because its pipe signal can reach another application thread; [the macOS safety decision](darwin-safety.md) records that path and its macOS 12 minimum for CPU budgets. Older systems return typed `Unsupported` before the cap changes; other kernel features retain their existing operating-system support.

The 2026-10-24 kernel decision for #278 gives that diagnostic a best-effort 100-millisecond grace period. The action waits only for a lock-free completion acknowledgement, using async-signal-safe monotonic clock queries, then calls `_exit(2)` regardless of output progress. A failed clock query exits immediately. A full pipe, unavailable reader or stalled relay may prevent the diagnostic; none may prevent exit code 2. The action never changes stdout flags or the process-wide SIGPIPE disposition, reserves no timer signal and never performs a potentially blocking stdout write. The grace interval bounds diagnostic work after delivery; operating-system scheduling can still delay delivery or execution. Existing CPU and elapsed budgets remain unchanged.

Standard Rust has no signal-installation API; the existing checked resource wrapper does not supply a signal exit action. The small FFI boundary stays in the foundation's approved OS module and adds no dependency. Its private relay owns process-resource diagnostics only; geometry operations have no global state or dependency on it.

This configuration changes the whole process. Callers own restoration and per-operation deadlines. The elapsed watchdog interval and budgets are unchanged. CPU and elapsed expiry, concurrent worker exhaustion, an already-consumed CPU budget, reset, concurrent setters, OS refusal, a closed stdout pipe and a full live stdout pipe with parent/child descriptor flags checked are tested in fresh children. The same 12-second parent safety guard bounds these tests. The fixed buffer also has independent decimal fixtures for zero, negative values and both i64 extremes.
